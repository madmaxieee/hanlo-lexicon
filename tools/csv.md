# CSV exports and releases

[Maintenance guide](README.md) · [Terminology](../GLOSSARY.md)

Run commands from the repository root.

## Build CSV

```sh
python3 tools/lexicon.py build-csv
python3 tools/lexicon.py build-csv --canonical-and-contractions
```

The default command validates the repository and atomically writes
`dist/lexicon.csv`. Each output form is the `preferred_form` or one of the entry's
`accepted_forms`; every output form renders the entry's readings the same way.
Exports always exclude pure-Hanji output forms, form by form: an entry preferring
`磕` with accepted `kha̍p` exports only `kha̍p`. Filtering ignores Hanji metadata
in `moe_forms` or `hanji_forms`. Any ASCII hyphen makes a form exportable, so
`後--日`, `落--去`, `--落-來`, and `--啊` are included. Other punctuation, spaces
and combining marks do not. Both UTF-8 files have columns `tl,preferred_form`,
no header row by default for TaigiKeyboard import, LF line endings, and rows
sorted by written form and then reading using Unicode code-point order. Identical
rows are emitted once, including rows shared by unrelated homographs. The TOML
records, IDs, source snapshots, and allocation counter are unchanged.

Add `--header` to any build variant to include the exact `tl,preferred_form`
header row. This writes to the same output filename; the reported row count
counts data rows only. An empty export without a header is a zero-byte file.

Use `--canonical-and-contractions` to export each included entry's
`preferred_form` with its `canonical_tl`, plus a row for each contraction, while
skipping other alternate readings. It writes `dist/lexicon-canonical-contractions.csv`,
leaving the regular export untouched. Contraction rows
follow the rule below. Sorting, deduplication, source validation, and the
pure-Hanji filter work the same way. Skipped alternate readings remain in the TOML
records. These builds do not try to align alternate spellings, so an unalignable
non-contraction alternate does not block them.

Each included entry contributes its `preferred_form` with its `canonical_tl`.
Each `alternate_readings` value also contributes, except that
`--canonical-and-contractions` keeps only the contraction rule:

- If the alternate has fewer syllables than the canonical reading, treat it as a
  contraction and use the complete alternate reading as both written form and TL,
  regardless of the preferred form's writing system. For example, `tann仔` with
  canonical `tann-á` and alternate `ta̋nn` produces `tann-á,tann仔` and `ta̋nn,ta̋nn`.
  The pure-Hanji entry filter still applies before generating rows.
- Otherwise, if the preferred form contains only Hanji apart from hyphens and
  other separators, retain it for each reading: `後--日` produces both
  `āu--ji̍t,後--日` and `āu--li̍t,後--日`.
- For fully romanized forms, use each alternate reading as its written output.
- For mixed forms, preserve Han characters and separators, and replace only the
  romanized syllables with the corresponding syllables of the alternate reading.
  Alignment requires one Han character or romanized syllable per reading syllable,
  with the written romanization matching the canonical reading. Longer alternates,
  mismatched spellings, or changed neutral-tone boundaries require explicit review;
  the build fails before replacing the CSV instead of guessing a spelling.

Reading syllables are nonempty runs separated by whitespace or ASCII hyphens
(`-` or `--`); tone marks and nasalization remain part of the syllable. The
exporter does not infer internal syllable boundaries in unseparated romanization.
For mixed-form alignment, each Han character or contiguous Latin run (including
combining marks, digits and apostrophes) counts as one written unit. Separators
are preserved in aligned outputs; contracted outputs preserve the alternate
reading verbatim.

For example, `beh` with alternate `bueh` produces:

```csv
beh,beh
bueh,bueh
```

A mixed entry `想beh` with readings `siūnn-beh` and
`siūnn-bueh` produces
`siūnn-beh,想beh` and `siūnn-bueh,想bueh`. Likewise, `beh食飯` with alternate
`bueh-tsiah-pn̄g` produces `bueh-tsiah-pn̄g,bueh食飯`. If only a Han-written
syllable changes pronunciation, its written form stays the same: `hip相` supports
both `hip-siòng` and `hip-siōng`.

These output spellings are generated by `spelling_readings(entry)`; alternate
readings stay in one editorial record, with the original ID and provenance.
`moe_forms` are evidence fields and do not generate output rows. All review statuses
are included; exporting does not mark entries reviewed. Tone marks, spaces, and
single/double hyphens are preserved.

`dist/` is ignored. A validation failure leaves an existing CSV untouched. The
build shares the maintenance writer lock to avoid racing with `add` or `format`.
MOE is fetched and verified only when required by source citations, using the
same pinned cache as validation.

The manual **Build CSV** GitHub Actions workflow runs tests and both build
commands, then makes `lexicon.csv` and `lexicon-canonical-contractions.csv`
available in the `hanlo-lexicon-csv` run artifact. It can be run from the repository's Actions tab.
Local builds need no GitHub account
or remote. JSON exports remain unimplemented.

## CSV releases

The **Release CSV** workflow runs on pushes to `main` and on pushes of tags
matching `v*`. A push to `main` runs only when it changes `entries/`, `sources/`,
`references/`, Python files under `tools/`, `RIGHTS.md`, or the workflow itself.
It publishes a release tagged with the UTC date, such as `v2026.11.08`; later
releases on the same day get `v2026.11.08.2`, `v2026.11.08.3`, and so on. If the
commit already has a tag, the push makes no new release. The workflow tests the
maintenance tools, checks formatting, validates the data, and builds both CSVs
with the local commands. It packages `lexicon.csv`,
`lexicon-canonical-contractions.csv`, `RIGHTS.md`, and `SHA256SUMS` covering the
CSVs and the rights file, then creates a draft
release with those assets before publishing it. Tags with a
hyphen, such as `v0.1.0-rc.1`, become prereleases. Existing releases are never
overwritten; a failed publish can leave a draft for the maintainer to inspect.

To release a published commit while using Jujutsu, create a tag through the GitHub
API (replace the version and full commit SHA):

```sh
gh api --method POST repos/madmaxieee/hanlo-lexicon/git/refs \
  -f ref=refs/tags/v0.1.0 -f sha=FULL_COMMIT_SHA
```

Creating the tag with your authenticated GitHub account triggers the workflow.
Use a new version for each release. Publish the commit to `main` with `jj git push`
before tagging it. The workflow checks out the tagged commit, never a moving
branch head. Source reuse notices remain part of every release; exporting does
not change review statuses or establish a new license.

For a dry run, select **Release CSV → Run workflow** on `main` and leave `publish`
unchecked. This runs the complete build and uploads a run artifact without a tag
or release. To publish an existing tag manually, dispatch on that tag with
`publish=true` (for example, `gh workflow run release-csv.yml --ref v0.1.0 -f
publish=true`). This also supports tags created by another workflow whose default
GitHub token does not trigger a new workflow run.

Download the assets from the repository's Releases page and verify them in the
same directory with `sha256sum --check SHA256SUMS` (macOS: `shasum -a 256 --check
SHA256SUMS`). The CSV's contents and review-status policy are described above.
